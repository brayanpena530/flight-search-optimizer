<RichText id="outcome">

### Outcome

This change implements the first approved slice from the visual plan: Houston to New York route coverage and a thinner browser provider layer. The backend `/api/providers/search` route is now the source of truth for provider ordering, fallback warnings, diagnostics, insights, and ranked itineraries.

The direct search smoke for `HOU` to `NYC` returned four accepted itineraries with airport expansion `IAH,HOU -> JFK,LGA,EWR`; the top option was `Outbound Southwest balance + Return United balance` with `$11.20` cash outlay.

The continuation added dependency-free `.env` loading for local provider credentials, a checked-in `.env.example`, and a focused Node test suite that locks down validation, airport expansion, sample ranking, and the backend search route. The United worker now also supports `UNITED_AWARD_IMPORT_PATH`, which lets normalized United award data feed the existing automation lane before full browser automation exists.

The latest continuation adds adult traveler count across the UI, normalized state, ranking engine, Amadeus cash search request, and result display. Cash fares, award taxes, miles, transfer points, and balance checks now scale to the full party.

The current continuation adds configurable Amex and Chase card-travel redemption rates. These create additional payment options that can offset cash fares directly with bank points, while leaving airline transfer redemptions and cash fares available for comparison.

The current optimizer fix makes `rankingFocus` apply to payment-method selection inside each itinerary, not only to the final itinerary sort. Effective-cost searches can now choose cash over a lower-cash point redemption when the user's point valuation makes cash economically cheaper. Award-program scope is also enforced in the ranking engine so direct miles and bank transfers cannot use unchecked airline programs.

The current award-ingestion slice generalizes normalized award imports from United-only to every selected airline worker. Each program can point at its own JSON file, and worker failures are isolated so one bad import path does not prevent other configured award programs from contributing results.

The current provider-resilience slice makes empty or fully failed award automation fall through to the next award source. The backend keeps the failed worker details in the response, adds a warning, and can still rank fallback sample awards instead of returning a misleading empty automation result.

The current result-transparency slice adds a structured value breakdown to each itinerary and renders it under every result card. Users can now see the cash fare baseline, cash saved, point opportunity cost, time preference penalty, and final effective cost behind the ranking.

The current import-safety slice validates normalized award imports before they reach ranking. Imported segments now need a positive cash/reference fare, positive miles, positive duration, and valid taxes/stops, so bad award exports cannot create fake free-cash options or invalid cpp math.

The current cash-bookability slice separates reference fares from bookable cash fares. Award-only imports still use their reference fare for cpp and effective-cost math, but they no longer generate cash or card-travel payment options unless a cash-capable source supplies the same segment.

The current live-cash normalization slice fixes Amadeus multi-traveler pricing. Amadeus returns `grandTotal`/`total` for the requested travelers, while the optimizer contract stores segment `cashPrice` per adult and scales it once in `search-engine.mjs`. The mapper now divides Amadeus totals by the requested adult count before ranking, and a fake local Amadeus test verifies a two-adult round trip totals `$800`, not `$1,600`.

The current inline-import slice makes the award import lane usable from the local app. The planner now accepts pasted award JSON, sends it as `awardImports` in the backend search request, validates the high-level program shape in `search-state.mjs`, and lets each selected airline worker prefer inline request data before env-var import paths or sample fallback. A backend search test posts inline Southwest award data through `/api/providers/search` and verifies the automation worker reports `inline-southwest-awards`.

The current airline-program expansion adds American and Alaska as direct-mile programs across the form, normalized search state, automation worker registry, inline/env import contract, display labels, docs, and tests. No Amex or Chase transfer path was added for those programs; they can rank when the user has direct airline miles or imports award data for that program.

The latest configuration cleanup centralizes airline program metadata in `search-config.mjs`. `search-state.mjs`, `automation-workers.mjs`, `search-engine.mjs`, and `app.js` now derive allowed programs, default award scope, balance normalization, worker registration, form field reads, labels, award-program checkboxes, and airline balance inputs from `AIRLINE_PROGRAMS` / `AWARD_PROGRAM_IDS` instead of repeating the same airline list in each file.

The current transfer cleanup centralizes transfer partner metadata as `TRANSFER_PARTNERS`, derives `PARTNER_MAP` from it for the ranking engine, generates transfer-ratio controls in the browser, and normalizes transfer ratios from the same source. The static United balance field was also removed from the bank-card row so generated airline balances are the only airline-balance controls.

The current time-preference slice makes the soft preference penalty visible and configurable. The form now sends `timePreferencePenaltyDollars`, `search-state.mjs` validates it, and `search-engine.mjs` uses it per missed leg when calculating the visible value breakdown.

The current insight and balance-impact slices make the result guidance more actionable. `buildSearchInsights` now keeps each bucket winner's booking method, points or miles used, cash savings, and time penalty; `search-engine.mjs` also attaches `balanceImpact` to each ranked itinerary so the API can show starting balance, amount used, and remaining balance for every touched currency. `app.js` renders both the flexible-date insight tradeoffs and the per-result balance impact row.
